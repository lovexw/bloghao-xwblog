# 2026-10-07 开发计划：会员 / 积分 / 排行榜（A·B 双机并行）

双机双 AI 并行开发模式与协作公约。分工草案之外的最终分配由用户拍板；两机开工前都必须读完
`AGENTS.md`、`docs/ROADMAP.md`（会员体系 + 排行榜两节）与本文档。

## 0. 模式结论

**可行，有四个前提**：契约先行、地基先行、文件分治、单点集成。本仓库的合并风险点集中
在少数热点文件（`src/api.ts`、`public/admin/app.js`、`schema.sql` ⇄ `src/db.ts` 双处同步、
settings 键），且积分/排行榜的数据源就是 `members.points`（依赖会员地基）。裸并行必然撞车，
按下述公约并行则两机互不阻塞。

## 1. 开工前用户必须拍板的三件事（ROADMAP「待拍板决策」）

1. **升级路径**：赞赏码手动升级 / 兑换码 / 积分达标自动升级（可组合，建议先选一种落地）
2. **注册门槛**：起步为「用户名 + 密码 + 可选邮箱」+ 蜜罐限流；是否加 Turnstile（C7）
3. **积分规则**：获取/消耗数值与单日上限（如评论 +2、每日登录 +1）；顶级会员具体权益

三项未定时：A 序列可先做与决策无关的地基（表结构、注册登录、会话），积分数值用常量表
集中一处（`src/points.ts`），拍板后只改一个文件。

## 2. 分工草案（最终由用户分配 A / B）

### A 序列 · 后端地基与会员 P1 服务端（src/ 侧）

- **地基提交（Step 0，最先落）**：`members` 表 + `comments.member_id` + `posts.min_tier` +
  积分账本表——`schema.sql` 与 `db.ts` SCHEMA_COLUMNS 两处同步，`ensureSchema` 迁移，
  附 tests；此提交落地后 B 才能 rebase 动任何依赖表结构的代码
- 注册 / 登录 / 退出（复用 `auth.ts` PBKDF2 + 独立 `xw_member_session` Cookie）+ 限流蜜罐
- 评论三路挂会员身份（走 `publicComment` 公共核心，不抄流程）
- 积分规则引擎（常量表集中 `src/points.ts`）+ 累计落库 + `/rank` 数据接口
- 会员中心数据 API、付费墙服务端截断 + 防泄漏清单逐项（RSS / 公开接口 / 搜索 / 卡片摘要）
- 后台会员管理 API；对应后端 tests

### B 序列 · 前台与后台 UI 层（public/ + src/themes/ 侧）

- 五主题：登录框、会员中心卡、付费墙遮挡层（390px 验证、聚焦字号 ≥16px、safe-area）

- 对应扩展 tests/themes.test.ts 与后台交互自查

## 3. 协作机制

1. **契约先行**：开工第一件事，两机共同确认 API 端点清单（路径 / 方法 / 入参 / 出参 JSON
   形状）、settings 新键表、主题渲染参数（registry.ts 命名类型扩展），登记进本文档附录
   或随 Step 0 提交；之后改契约必须两端知情，不许单方面变（**已登记：见文末附录 A，B 机
   有异议先对齐再动 UI**）
2. **地基先行**：A 的 Step 0 地基提交是 B 的开工闸门；B 在此之前只做不碰表结构的纯 UI
   骨架与 fixture
3. **分支模型**：`main` 为集成分支；两机各自工作分支 `dev/a-*`、`dev/b-*`，随时推 origin
   互读进度；**合并回 main 只由树莓派（集成机）执行**
4. **节奏**：小步快跑——每完成一个可测试切片即 commit + push origin；开工前一律
   `git pull --rebase origin <分支>`；提交信息沿用前缀中文风格
5. **质量门禁**：每序列提交前 `npm run typecheck` + `npm test` 必须过；任何进 main 的合并
   在树莓派上加跑 `npm run smoke`；UI 改动按 AGENTS.md 过 390px；新表/列必须 schema.sql
   与 db.ts 两处同步（docker-poc shim 若受影响同步并跑其 smoke）
6. **冲突仲裁**：契约 > 本公约 > AGENTS.md；同一文件同段落的竞争改动，后改方负责 rebase
   解决；schema 语义冲突一律回退到契约层重新对齐，不许两头各改一份硬合

## 附录 A · API / 数据契约 v0（2026-10-07，随 Step 0 地基提交登记）

由 A 机起草、随 Step 0 落库；B 机 UI 一律按本契约用 fixture 驱动，有异议通过各自工作分支
的 commit 对齐后修订版本号，不许单方面变更。

### 数据语义（Step 0 已落库）

- `members` 表：访客注册的站内身份。**架构红线：与 users / sessions 彻底分离**（users 只承载
  管理员，`/api/auth/setup` 靠 `countUsers() === 0` 判断首装）
- `members.tier`：`normal | coffee | top`，等级序 normal(1) < coffee(2) < top(3)
- `posts.min_tier`：INTEGER 0–3 的可见门槛——**0=公开、1=登录会员可见、2=咖啡会员及以上、
  3=顶级会员**；判定式 `viewerRank >= min_tier`（游客 rank=0，normal=1）
- `comments.member_id`：0 = 游客；>0 = members.id，该评论带会员昵称/头像/档位徽标
- 积分：余额冗余在 `members.points`，明细在 `member_points_log`（delta 可负，`reason` 存
  规则键，`ref_id` 关联评论等对象）
- 会员会话：独立表 `member_sessions` + 独立 Cookie **`xw_member_session`**（HttpOnly /
  Secure / SameSite=Lax / 30 天），与管理员 `bloghao_session` 互不干扰
- 数据库三张新表在 schema.sql 与 db.ts SCHEMA_TABLES 均已登记；`tests/member-schema.test.ts`
  守「两处同步」不变量；备份含 members / member_points_log，不含 member_sessions（临时凭证）

### settings 新键（随端点提交实现进 DEFAULT_SETTINGS；谁加谁登记）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `membersEnabled` | `'0'` | 会员体系总开关；关闭时前台无登录入口、`/api/member/*` 返回 404 |
| `membersAllowRegister` | `'1'` | 开放注册开关（仅 membersEnabled 开时生效；关闭后只可登录） |

积分规则数值**不进 settings**：常量表集中 `src/points.ts`，用户拍板后单点修改（本公约第 1 节）。

### API 端点（A 提供；B 的 UI / fixture 按此驱动）

| 端点 | 方法 | 入参 | 出参 / 约定 |
| --- | --- | --- | --- |
| `/api/member/register` | POST | `{username, password, email?}` | `MemberSelf` + Set-Cookie；403 注册关闭 / 400 校验失败（用户名占用等） |
| `/api/member/login` | POST | `{username, password}` | `MemberSelf` + Set-Cookie；封禁账号 403 `{error:'banned'}` |
| `/api/member/logout` | POST | — | `{ok:true}` + 清 Cookie |
| `/api/member/me` | GET | — | `{member: MemberSelf \| null}`，**恒 200**（前端据此渲染登录框或会员卡） |
| `/api/member/points` | GET | `?cursor` | `{balance, items:[{delta, reason, note, createdAt}]}`（新→旧，cursor 翻页） |
| `/api/public/rank` | GET | `?limit=10` | `{items:[{rank, id, username, displayName, avatar, tier, points}]}`，只含 active，按 points DESC |
| `/api/admin/members` | GET | `?query=&page=` | `{items: MemberSelf[], total}`（管理口径含 email/status） |
| `/api/admin/members/:id` | PUT | `{tier?, status?, pointsDelta?, note?}` | 更新后的 MemberSelf；`pointsDelta≠0` 时同步写账本（reason=adminAdjust） |

- `MemberSelf`（公开口径）= `{id, username, displayName, avatar, tier, points}`；管理口径追加
  `email, status, createdAt, lastLoginAt`
- 评论三路（文章 / 留言板 / 微博评论，走 `publicComment` 公共核心）：请求带会员会话时服务端
  自动挂身份，昵称 / 邮箱 / 网站字段忽略；**响应 item 追加 `member: {id, displayName, tier} | null`**
- 全部端点沿用仓库既有约定：写操作限流 + 蜜罐、`:id` 走 `parseId()`、错误统一 `{error}`

### 主题渲染参数（registry.ts 命名类型扩展；B 用 fixture 驱动，390px 硬要求照办）

- 所有页面数据对象追加可选 `member?: MemberSelf | null`（null/缺省 = 渲染登录入口）
- `PostData` 追加 `minTier: number` 与 `locked: boolean`——locked 时 `content` 已被服务端截断
  为 teaser（**截断在 A，防泄漏清单同步 RSS / 公开接口 / 搜索 / 卡片摘要**），B 渲染付费墙遮挡层
- 新增命名类型 `RankData { items: {rank, id, displayName, avatar, tier, points}[] }`；主题可选实现
  `rank(d)` 渲染（runtime guard 缺省回退通用壳，同 page() 先例；navActive 约定 `rank`）
- 评论渲染：`item.member` 非空时加档位徽标（文案：普通 / 咖啡 / 顶级）

### 积分规则键（`src/points.ts` 常量表，数值待用户拍板先占位）

`comment`（过审计入）、`dailyLogin`、`adminAdjust`；各规则带单日上限，防刷靠既有蜜罐 + 限流叠加。
